# Prefill/decode 분리 실험과 8건 전체 대기 fallback

요청한 두 수준의 실험을 완료했다. Prefill과 decode 양쪽에서 배치 구성에 따른 차이를 확인했다. 특정 레이어나 GPU 커널을 조사해야 더 좁힐 수 있으므로 분석을 종료하고, 혼합 파이프라인을 최대 8개 요청 전체 대기 방식으로 전환했다.

## 실험 1: 배치 방식 변경

동일한 24건·6개 feature·32K·스텝 8,192토큰·최대 8요청·thinking 1,024토큰·출력 2,048토큰 조건을 사용했다.

| 방식 | 계측 시간 | 생성 토큰열 차이 | 이진 판정 차이 |
|---|---:|---:|---:|
| 전체 대기 대비 연속 보충 | 63.95초 → 60.61초 | 24/24건 | 6/144개 |

이번에는 최초 8건도 달랐다. 앞선 진단의 16/24건과 달라진 개수를 비교해 효과 크기를 추정하면 안 된다. 완료 대기 정책 외에 요청 제출 시점에 따른 엔진 내부 prefill 묶음 변화도 섞여 있다. 이 실험의 시간은 계측된 24건 값이며 기존 200건 벤치마크를 대체하지 않는다.

## 실험 2: 동일한 토큰 이력에서 단계 비교

실험 1에서 생성이 달라진 첫 4개 공고를 입력 순서로 선택했다. 정답 라벨은 선택에 사용하지 않았다. 문서 입력 뒤에 분기 직전까지 공통인 생성 토큰을 붙여 이력을 고정했다. 모든 조건을 두 번 반복했다.

| 공고 | Prefill 단독 → 8건의 다음 토큰 | Decode 중 배경 요청 추가 결과 |
|---|---|---|
| PPS-DEV-01 | ` set` → ` item` | 8번째 토큰부터 선택이 달라짐 |
| PPS-DEV-02 | `The` → `The` | 8번째 토큰부터 선택이 달라짐 |
| PPS-DEV-03 | ` based` → ` (` | 8번째 토큰부터 선택이 달라짐 |
| PPS-DEV-04 | ` list` → ` procurement` | 16토큰 안에서 선택은 같지만 점수는 달라짐 |

**Prefill:** 캐시를 비운 뒤 고정된 전체 이력을 입력하고 다음 토큰 하나만 생성했다. 단독과 배경 요청 7개가 있는 조건을 비교하자 4개 중 3개에서 선택이 달라졌고, 두 번 모두 재현됐다. Prefill 경로만으로도 차이를 만들 수 있다는 증거다. 과거 실행의 누적 KV 텐서를 그대로 재현한 실험은 아니다.

**Decode:** 같은 이력으로 단독 시작하고 첫 토큰 반환 후에만 배경 요청 7개를 추가했다. 모든 비교에서 첫 토큰과 기록된 상위 10개 후보 점수는 같았다. 생성 이력이 같은 구간만 비교했을 때 4개 사례 모두 4번째 토큰의 점수부터 달라졌으며, 3개 사례는 8번째 토큰 선택이 바뀌었다. 같은 조건의 반복 결과는 토큰과 기록된 점수까지 전부 동일했다.

단계 확인용 생성은 JSON 제약과 thinking budget 마스크를 사용하지 않았다. 이 조건은 실제 판정 파이프라인에 적용하지 않았다. 기록한 점수는 상위 10개 후보의 log probability이며 원시 logit이나 레이어별 수치 오차가 아니다. 후보 점수가 동률이면 선택된 토큰과 top-k의 rank 순서가 다를 수 있다.

## 중단 및 fallback

Prefill만 또는 decode만의 문제로 좁혀지지 않았다. 특정 레이어·커널의 연산을 확정하려면 사용자가 제외한 하위 수준 분석이 필요하므로 여기서 중단했다.

현재 실행 진입점은 `scripts/run_batch_fallback.py`이다. `BatchedPredictor`는 먼저 끝난 응답을 보관하고 현재 묶음 전체가 끝나면 제출 순서대로 반환한다. 다음 묶음은 그 뒤에 들어간다. 기존 continuous 코드는 과거 실험 재현용으로 보존했다.

- 그룹 구성 유지: instant 4그룹은 OFF, 나머지 6개 feature 그룹은 ON/1,024토큰.
- 원문·법령 프롬프트, v2/v3 규칙, 캐시 seed 의존성, RAG·재시도 정책 유지.
- 48개 단위 테스트 통과.
- 실제 혼합 16건·24항목을 145.38초에 실패 없이 완료. 정상 재시도 1회를 포함해 81개 모델 요청.
- 11개 묶음 모두 전체 완료 후 다음 묶음을 제출함을 로그로 검증.
- 최초 8건 전체 완료 후 27.73ms에 9번째 요청 제출.

전체 대기는 요청 보충으로 인한 변화를 줄이는 선택이다. 배치 불변성이나 과거 F1 복원을 보장하지 않는다. 이번에 fallback의 200건 성능을 다시 측정하지 않았으며, 16건 검증 시간을 200건에 직접 외삽하지 않는다.

```bash
uv run --locked python scripts/run_batch_fallback.py --output-dir NEW_OUTPUT_DIR
```

기본 입력은 dev 200건이다. `--limit 16`은 실행 검증용이다. 원시 결과는 `probes.json`, 비교는 `summary.json`, 실행 검증은 `validation.json`과 `fallback16/`에 있다.
